KitCode Reward Logic Comparison

A short comparison of two ways to run KitCode rewards: a plain-text skill that guides the agent, or a CLI/runtime that does the tracking work.

Skill-only is easiest to try. It is mostly instructions for the agent. Good for demos, manual checks, and low-stakes encouragement. Fastest start
CLI/runtime is better for trusted rewards. It can track activity, save progress, feed dashboards, and make repeatable reward decisions. Best source of truth
1. Setup & daily flow

What happens once, and what repeats?

This is the practical user journey from first setup to checking a reward.

Step Plain-text Skill Only CLI / Runtime
Before setup Codex or Claude must support local skills. File access is only needed if the agent will inspect code. A skill can be invoked by normal text. Slash shortcuts need separate agent support. The current package needs Node.js 20+. Git is optional, but helps show commit activity. Check 
node --version
git --version
One-time setup Install or copy the skill text so the agent knows the reward rules. Example input 
Install this KitCode skill. If slash shortcuts are supported, add /kitcode-check.
 Turn on the Codex or Claude integration once for that agent. This can install the skill too, but the skill points back to the CLI/runtime as the source of truth. Command 
npx @onedigitas/kitcode codex on
npx @onedigitas/kitcode claude on
After setup, user can ask 
Use the KitCode skill and check the CLI-backed reward status.
Per project Tell the agent which folder is the starting point. Any baseline is manual unless the agent saves one with tool access. Example input 
Use this folder as my KitCode baseline.
 Add the project once. Existing code becomes the baseline and does not count as new progress. Command 
npx @onedigitas/kitcode add .
Each work session Ask the agent to check manually. Nothing runs in the background. Example input 
KitCode check my progress.
 Start or keep the tracker running, then code normally. Command 
npx @onedigitas/kitcode track
Reward check The agent can explain a likely reward, but it should say when the result is only a manual estimate. Manual estimate Open the dashboard or mini window to see saved progress and reward status. Command 
npx @onedigitas/kitcode dashboard
2. What it can actually do

Instruction versus tracking system

This is the main difference: skill-only can guide the agent, while CLI/runtime can own the data.

Capability Plain-text Skill Only CLI / Runtime
Automatic tracking No. It only runs when the user invokes the agent. Yes. It can track while the user works.
Save progress Only if the agent has file tools and writes a state file. Yes. It can own local state in a controlled format.
Count = or commits Only during a manual check, if the agent can inspect files or Git. Yes. It can compare snapshots and read Git activity repeatedly.
Dashboard data No live dashboard data unless another system provides it. Yes. It can feed the mini window and dashboard.
Reward trust Best-effort. Good for low-stakes messages. Repeatable. Better for campaign reporting and verified rewards.
3. Which should we choose?

Simple decision

The right option depends on whether KitCode is just a friendly guide or the source of truth for rewards.

Choose skill-only when...

You want the lightest setup, a demo, a manual check, or a friendly reward narrative.

Choose CLI/runtime when...

You need automatic tracking, saved progress, dashboard data, fairness, or reward proof.
